# Module "io"

## Overview

Allows writing and reading objects graphs from and to persistent storage like XML files, including deferred reference resolution while reading.

Business objects that want to be part of persistent object graphs need to implement the `Storable` interface. Framework-provided implementations of `StoreWriter` and `StoreReader` can then be used by the business objects to read and write their properties and object references, using methods like `StoreWriter.writeInt` and `StoreReader.readInt`.

In order to store object references, business classes treated by the IO framework must be registered with the `TypeMap`, whose single instance is accessible at `IOModule.typeMap`. Registrations map external class identifiers to effective class names of `Storable` implementations.

Modules using the `io` functionality will have to decide on the external storage format. `io` provides implementations of the `StoreReader` and `StoreWriter` interfaces for XML data, namely `StoreXmlReader` and `StoreXmlWriter`. On the JVM platform, they can be created with an instance of `ElectricXmReader` and `ElectricXmlWriter` respectively, both wrappers for the "Electric XML" library imported by the Jabbah framework. On the JS platform, the browser's own XML library is used.

For an example of how reading and writing is initiated on the application layer, checkout the class `AbstractFileLibraryPersistenceService` in the `graph` library, and there the methods `loadMetaGraph` and `storeMetaGraph`.

There are also various utilities like `StorableCloner`, which can clone entire object graphs by transparently writing them to a buffer and reading it back, thereby providing a deep copy of the graph.

## Object references

In order to be able to write and read entire object graphs including object references, `io` can not use IDs of the business objects, because they are typically only unique within their context (e.g. a circuit model), but not within the context of the stored graph (e.g. a circuit with separate model and view objects).

This is why `io` uses "global" IDs generated by itself on-the-fly. Whenever a `Storable` needs to store a reference to another `Storable`, it asks the `StoreWriter` to provide a global entity for the referenced object. This is delegated to an `IdentityProvider` implementation that maintains a mapping between object references and IDs it provided from them. When being read back from storage, the `Storable` uses a `ReferenceResolver` to resolve the persisted global ID back to an object reference.

See `AbstractGraphElementView` in the `graph` module for an example application, where view objects need to resolve a reference to their model object when being deserialized.

## Example

The following (stripped down) example from an Antares XML circuit file containing a switch and an LED shows how IDs are used.

````
<?xml version='1.0' encoding='UTF-8'?>
<metaGraph _id='0' appVersion='2.0.0' manualContainer='true'>
  <graph>
    <graphStorable _id='1'>
      <model>
        <graph _id='2' type='digital'>
          <elements>
            <switch _id='3' id='1' delay='1000'/>
            <led _id='4' id='2' delay='0'/>
          </elements>
        </graph>
      </model>
      <view>
        <graphView _id='12' lightColor='red' signalRepresentation='hex'>
          <components>
            <switchView _id='17' id='1' rot='0' filled='true' stroked='true' modelId='3' x='-504.0' y='-371.0'/>
            <ledView _id='18' id='2' modelId='4' x='-469.0' y='-371.0'/>
          </components>
        </graphView>
      </view>
    </graphStorable>
  </graph>
</metaGraph>
````

All globally referencable IDs are contained as `_id` attributes. For example, `<switchView>` reference its `switch` model using the attribute `modelId='3'`, which points to the attribute `_id='3'` in the `<switch>` element.

Note also how `<ledView>` is used as XML element name, and not the LED's Kotlin class name `LEDView`, which decouples persistent files from implementation class names, bridged by the `TypeMap` registrations.
